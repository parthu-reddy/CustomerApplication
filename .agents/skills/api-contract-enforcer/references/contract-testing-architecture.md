# Contract Testing Architecture

This reference document provides the deep architectural context for the `api-contract-enforcer` skill.

## The Problem: Interservice Boundary Fragility

Once data successfully negotiates the frontend-to-backend boundary, it frequently enters a distributed labyrinth, traversing multiple microservices via HTTP REST, GraphQL, or gRPC protocols. Historically, engineering teams relied on End-to-End (E2E) integration tests to verify these interactions. However, E2E tests require standing up the entire world of microservices simultaneously, making them notoriously slow, computationally expensive, highly fragile, and difficult to maintain.

To mathematically guarantee interservice data integrity without the overhead of integrated testing, the architecture must employ **API Contract Testing**. Contract testing is the rigorous discipline of verifying that an API provider and its respective consumers continuously honor a shared, machine-readable interface agreement. This agreement comprehensively covers endpoints, request and response schemas, HTTP methods, status codes, authentication mechanisms, and data types. If either the provider or the consumer violates the contract, the test fails instantly in isolation, serving as an early indicator of integration failure long before the code reaches a staging environment.

## Modalities of Contract Testing

| Testing Modality | Tooling | Mechanism and Agent Verification Directive |
| :---- | :---- | :---- |
| **Consumer-Driven Contracts (CDC)** | Pact | The consumer dictates its exact requirements. It generates a "contract" (a Pact file) documenting expected requests and minimal required responses. The agent must verify that the provider periodically pulls this contract and executes provider verification tests against its actual implementation, utilizing provider states (mocked database setups) to satisfy the consumer's request. |
| **Schema-First Property-Based Testing** | Schemathesis | The provider's OpenAPI or AsyncAPI specification acts as the universal baseline. The agent must run Schemathesis to automatically generate property-based tests derived directly from the schema. It bombards the API with thousands of edge-case payloads to ensure the service never throws unhandled 500 exceptions and that all responses strictly match the documented Zod/OpenAPI definitions. |

## CI/CD Integration

The agent must verify that contract testing is treated as code:
- Scan the CI/CD pipeline configuration (e.g., GitHub Actions or GitLab CI) to ensure that specifications are linted on every pull request using rulesets like Spectral, enforcing descriptions and complete error-response coverage.
- Raw test logs are tedious and prone to misinterpretation. The agent's instructions strictly forbid manually reading the log output. Instead, the agent must parse the exit codes and structured JSON reports generated by the testing tools.
- If a contract violation is detected—such as a backend service dropping a required property that a frontend component relies upon, or changing a data type from an integer to a string—the agent must generate an Artifact explaining the exact nature of the breach. It will then propose a resolution, either by updating the consumer to adapt to the new API design or by reverting the provider's breaking change, depending on semantic versioning rules.
